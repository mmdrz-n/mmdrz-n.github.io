"It works on my machine" is a network statement

Most production bugs that get escalated to the network team are not network bugs. And most "the app is slow" tickets that land with developers are not code bugs. Both sides lose hours because nobody owns the space between the code and the cable.

You don't need a CCNP to cross that gap. You need a mental model of what one request does on its way out of your laptop, and a handful of commands to check each step. That's what this post gives you.

The life of one HTTPS request

Take a boring line of code: fetch("https://api.example.com/users"). Before a single byte of your JSON arrives, roughly six things have to go right:

  1. DNS. The OS asks a resolver for the IP of api.example.com. Wrong answer, stale cache or split-horizon DNS here, and everything after is aimed at the wrong place.
  2. Routing decision. Your machine compares that IP against its routing table. Not in your own subnet? The packet goes to the default gateway.
  3. ARP. To hand the packet to the gateway, your NIC needs the gateway's MAC address. ARP asks "who has 192.168.1.1?" on the local segment.
  4. Firewall policy, session and NAT. Your first SYN to port 443 hits the edge firewall. It checks its policy, creates a session entry and rewrites your private source IP to a public one, remembering the mapping so the reply can find its way back. This is where firewalls decide whether you get to talk at all.
  5. TCP handshake. SYN → SYN-ACK → ACK completes through that session.
  6. TLS handshake. Certificates, SNI, cipher negotiation. Inspection proxies and expired intermediate certificates live here.

Only after all six does HTTP happen. When a request "hangs", the question is simply: which of these six steps didn't finish?

Timeout vs. refused: the most useful distinction in debugging

If you only remember one thing from this post, make it this:

SymptomWhat it usually meansWhere to look
Connection refused (instant)The host is reachable and answered with a TCP RST. Nothing listens on that port.Service down, wrong port, app bound to 127.0.0.1 only
Connection timed out (slow)Packets are silently dropped. Nobody answered at all.Firewall policy, security group, missing route, wrong IP
Could not resolve hostStep 1 failed.DNS resolver, hosts file, VPN DNS settings
TLS / certificate errorTCP worked, step 5 failed.Certificate chain, SNI, SSL inspection proxy
Small requests work, big ones hangAlmost always MTU.VPN tunnels, PPPoE, blocked ICMP
Rule

A firewall that denies usually drops. That's why a blocked port looks like a timeout, not an error. "Refused" means you got through the network and the server itself said no.

The MTU trap

Ethernet frames carry 1500 bytes of payload by default. Wrap traffic in an IPsec or WireGuard tunnel and some of those bytes go to headers, so the effective size shrinks. If something in the path also blocks ICMP "fragmentation needed" messages, large packets vanish silently while small ones pass. The login page loads, the file upload never finishes.

You can test it in ten seconds. 1472 bytes of ICMP payload + 28 bytes of headers = exactly 1500:

# Windows: -f = don't fragment, -l = payload size
ping -f -l 1472 api.example.com

# Linux
ping -M do -s 1472 api.example.com

# macOS: -D sets the don't-fragment bit
ping -D -s 1472 api.example.com

If 1472 fails but 1400 works, you've found your problem. Lower the size until it passes; that number + 28 is your real path MTU.

A developer's network toolkit

Each tool checks one step from the list above. Learn them in this order:

# 1. DNS: what IP does this name resolve to?
Resolve-DnsName api.example.com        # Windows
dig +short api.example.com             # Linux / macOS

# 2-5. Can I reach the port at all? (routing + firewall + TCP)
Test-NetConnection api.example.com -Port 443
nc -vz api.example.com 443

# 6. Full request with TLS details and timings
curl -v https://api.example.com/health

# Where does the path die?
tracert api.example.com                # Windows
traceroute api.example.com             # Linux / macOS

# What is MY app actually listening on?
netstat -ano | findstr LISTENING       # Windows
ss -tlnp                               # Linux
Tip

When you open a ticket with the network team, paste the output of Test-NetConnection and curl -v. A ticket with "TCP 443 to 10.20.0.15 times out from 10.10.5.22" gets fixed in minutes. "The API is broken" gets fixed on Thursday.

What network engineers can borrow from developers

The bridge goes both ways. Developers have spent twenty years building habits that infrastructure people are only now adopting:

  • Version control for configs: a firewall policy change should have a diff and a reason, just like a pull request.
  • Automation instead of copy-paste CLI sessions. I wrote about that in Automating FortiGate Policies with Python.
  • Tests: a script that checks "can VLAN 20 still reach the file server?" after every change is a unit test for your network.

Takeaway

You don't need to become a network engineer. You need to know the six steps, the difference between a timeout and a refusal, and which command tests which step. That's the bridge. Walk it a few times and you'll never again lose a day to a problem that was "just the firewall".
