FortiGate Debug Flow: A Practical Cheat Sheet

"The firewall is blocking it" is a guess. Debug flow turns it into a fact. Here's the exact command sequence I use, how to read the output, and the five messages that explain 90% of dropped traffic.

Oct 20, 20263 min readby Mohammadreza Nobahari

When to reach for debug flow

Logs tell you what a policy decided. Debug flow tells you why: which route was chosen, which policy was checked, whether NAT happened and where the packet died. Use it when:

  • traffic is dropped but you see nothing in the forward traffic log,
  • you suspect routing, reverse-path or NAT problems,
  • a VPN tunnel is up but traffic doesn't pass,
  • someone insists "it worked yesterday".

The recipe

Always start from a clean state, filter as narrowly as possible, and limit the number of traced packets. Debug output on a busy firewall without a filter is a great way to make a bad day worse.

diagnose debug reset
diagnose debug flow filter clear
diagnose debug flow filter addr 10.0.10.25
diagnose debug flow filter proto 1
diagnose debug flow show function-name enable
diagnose debug console timestamp enable
diagnose debug flow trace start 20
diagnose debug enable

Now generate the traffic (here: a ping from 10.0.10.25, which is why the filter is proto 1 = ICMP). For TCP use proto 6 and, if needed, filter port 443.

When you're done, always turn it off:

diagnose debug disable
diagnose debug flow trace stop
diagnose debug reset

Reading the output

Each packet produces a short story. Read it top to bottom. These are the lines that matter:

You seeIt means
allocate a new session-…First packet of a new connection. Good, the FortiGate sees it.
Find an existing session, id-…Packet belongs to a known session. Policy is not re-checked.
find a route: … gw-x.x.x.x via portNThe routing decision. Wrong interface here = routing problem, not policy.
Allowed by Policy-5:Matched policy ID 5. Compare with the one you expected.
SNAT x.x.x.x->y.y.y.y:portSource NAT applied on the way out.

The five classic drops

1. Denied by forward policy check (policy 0)

Policy 0 is the implicit deny at the bottom. No policy matched. Check interfaces (srcintf/dstintf), address objects, service and schedule. Very often the traffic enters on a different interface than you think.

2. reverse path check fail, drop

Anti-spoofing (RPF). The FortiGate has no route back to the source via the interface the packet came in on. Typical causes: asymmetric routing, a missing static route for a remote subnet, or a VPN without a route for the remote network.

3. iprope_in_check() check failed on policy 0, drop

Traffic to the FortiGate itself (local-in) was denied. Classic example: pinging or managing an interface where PING/HTTPS/SSH administrative access isn't enabled, or a trusted-hosts restriction on the admin account.

4. No output at all

The packet never reached the FortiGate. Check your filter first, then the switch, VLAN tagging, the client's default gateway, and ARP.

5. Allowed, but no reply

The trace shows Allowed by Policy-N and a route out, but nothing comes back. The problem is downstream: the server's firewall, its default gateway, or NAT on the return path.

Sniffer: the companion tool

Debug flow explains decisions; the sniffer proves packets exist on the wire. Verbosity 4 shows the interface name, which is gold for spotting wrong-interface problems:

# filter, verbosity 4 (with interface), unlimited count, local timestamps
diagnose sniffer packet any 'host 10.0.10.25 and icmp' 4 0 l

Stop it with Ctrl+C. If you see the request leave port1 but no reply arrive, the FortiGate is not your problem.

Sessions: when the policy changed but nothing happens

Existing sessions don't get re-evaluated against new policies. If you fixed a rule and the client still fails, look at the session table:

diagnose sys session filter clear
diagnose sys session filter src 10.0.10.25
diagnose sys session filter dst 198.51.100.10
diagnose sys session list
diagnose sys session clear
Danger

diagnose sys session clear clears every session that matches the current filter. With no filter set, that is every session on the box, including your own SSH connection and everyone's VPN. Always run filter first and double-check it.

My checklist

  1. Reproduce the problem and write down source, destination, protocol and port.
  2. Sniffer: does the packet arrive, and on which interface?
  3. Debug flow: route → policy → NAT. Where does the story end?
  4. Fix one thing. Clear only the affected sessions. Test again.
  5. Turn debugging off and document what you found, for the next person.

Want to practice the routing side? Try the subnetting in your head method. Half of all "policy problems" turn out to be a wrong mask.
